## 프로젝트

### SurroAX — 멀티 에이전트 AI 플랫폼

**써로마인드** · 2026.09 ~ 진행 중 · PL, 풀스택 개발

**Tech** · React 19, Vite, TanStack Router, Expo, Tauri · Python, FastAPI, gRPC, PostgreSQL, RabbitMQ, Keycloak, OpenFGA, MCP

사용자의 요청을 여러 작업으로 나누고, AI 에이전트들이 의존 순서에 따라 처리하게 하는 사내 플랫폼입니다. 백엔드와 클라이언트(웹·모바일·데스크톱) 저장소를 처음부터 만들었고 공식 PL을 맡고 있습니다.

PL로서 팀장님이 받아온 요구사항을 기술적으로 검토하고, 작업 단위로 쪼개 진행을 관리합니다. 에픽 작업 191건 중 158건을 직접 작성했습니다. 초기 리뷰에서는 **설계 결정과 코드가 맞는지 대조해**, 하위 작업이 상위 작업의 권한을 그대로 물려받는 문제, DB 교착 때 요청이 사라지는 문제, 운영자가 끈 도구가 다시 켜지는 문제를 머지 전에 찾아 고치게 했습니다.

서비스와 클라이언트가 함께 늘어나는 제품이라, **서비스끼리 코드를 공유하지 않고 미리 정한 인터페이스(계약)로만 통신하도록** 구조를 잡았습니다. 계약 24종 중 18종을 처음 설계했고, 계약 검사와 하위 호환성 검사를 CI에 넣어 계약을 어긴 변경은 머지되지 못하게 했습니다. 이 검사는 동료 변경에서 오류 코드 값을 지운 호환성 위반을 머지 전에 잡았습니다. 운영해 보니 동시에 진행되는 작업들이 같은 계약 버전 번호를 잡아, 늦게 머지하는 쪽이 번호와 문서를 다시 고치는 일이 반복됐습니다. 작업마다 변경 내용만 적고 번호는 릴리스 때 한 번에 매기도록 규칙과 CI를 바꿨고, 이후 번호 충돌로 막힌 변경은 없었습니다.

작업 실행 엔진은 워커가 DB에 직접 상태를 쓰면 같은 규칙이 언어마다 흩어지고, 문서 파서 같은 워커까지 DB 쓰기 권한을 갖게 되는 문제가 있었습니다. **상태 전이를 DB 함수 한 곳에 모으고** 엔진은 그 함수를 감싼 gRPC 서비스로만 두었습니다. 워커는 DB 접속 정보 없이 작업을 받고, 접속 정보가 주어지면 기동을 거부합니다. 동시 선점이나 만료된 시도의 늦은 결과 같은 경합은 시험으로 고정했고, 같은 구조 위에 사람의 승인을 기다리는 단계와 예약 실행을 더했습니다.

Outlook·Teams 연동에서는 메일과 메시지 전송을 **되돌릴 수 없고, 다시 보내면 두 번 나간다**는 점이 문제였습니다. 쓰기 도구는 사용자가 승인해야만 호출되게 하고, 승인은 엔진 신호로만 받아 AI 모델이 승인을 꾸며낼 수 없게 했습니다. 승인을 기다리는 동안에는 워커 자리를 비워 다른 작업이 막히지 않습니다. 연동 MCP 서버(약 3,700줄)는 혼자 만들었습니다. 전송은 다시 시도하지 않고 결과를 보냄·실패·모름으로 나눠 중복 발송이 생기지 않도록 설계했고, 호출마다 직원 본인의 Microsoft 365 토큰을 받아 Microsoft Graph로만 보내며 서버에는 비밀 정보를 두지 않았습니다.

인증은 사내 공용 Keycloak을 빌리는 대신 자체 Keycloak을 두고 직원 로그인을 Entra에 직접 연결해, 로그인 화면이나 설정을 바꿀 때마다 다른 팀에 요청하지 않아도 되게 했고, 인가는 OpenFGA로 나눠 권한 모델을 시험으로 검증했습니다. 직접 개발한 범위는 작업 실행 엔진과 인증 서비스, MCP 게이트웨이(공동), 웹·운영 콘솔·모바일(Expo)·데스크톱(Tauri) 클라이언트와 BFF입니다. 프론트엔드는 BFF를 거쳐서만 백엔드에 접근하게 하고, BFF 코드가 DB 드라이버나 메시지 큐 클라이언트를 가져다 쓰지 못하도록 린트로 막았습니다. 고객사 관리자 화면과 운영 콘솔은 Figma 없이 아티팩트로 설계했습니다.

### SMDS 디자인 시스템과 Surro Q&A 웹

**써로마인드** · 2026.04 ~ 진행 중 · UI/UX 설계, 프론트엔드 개발

**Tech** · Next.js 15, React 19, Tailwind CSS 4, Radix UI, Storybook, Turborepo, pnpm

여러 서비스가 함께 쓰는 사내 디자인 시스템과, 이 디자인 시스템으로 만든 Surro Q&A 사용자 웹·운영 어드민입니다. 저장소 구조부터 배포까지 직접 만들었습니다.

디자인 시스템은 색상·그림자 같은 토큰과 브랜드별·라이트/다크 테마부터 설계했습니다. 처음에는 앱이 패키지 6개를 설치하고 디자인 시스템 내부 경로와 긴 테마 설정을 앱 CSS에 그대로 복사해야 해서 **도입 비용이 컸습니다**. 저장소 안의 패키지 구분은 유지하되 배포할 때 토큰·아이콘·훅을 하나로 묶고, 컴포넌트 스타일과 테마 설정은 미리 컴파일해 함께 배포했습니다. 이제 앱은 패키지 2개를 설치하고 CSS 세 줄만 쓰면 됩니다. 기획팀과 디자인팀에는 디자인 시스템을 기준으로 일하는 프로세스를 제안했습니다.

아이콘 이름은 자유 문자열이라 오타가 나도 에러 없이 아이콘만 사라졌고, AI 코딩 도구에 이름을 알려 주는 MCP 서버의 목록에도 실제로 없는 이름이 섞여 있었습니다. **등록된 이름만 허용하는 타입**으로 바꾸고 MCP 목록은 아이콘 라이브러리의 정식 파일명으로 다시 만들었습니다. 바꾸자마자 타입 검사가 두 앱에서 그려지지 않던 아이콘 네 곳을 찾아냈고, 이후 잘못된 이름은 빌드 전에 막힙니다.

채팅 페이지 첫 로딩에는 쓰지 않는 문서 변환·그래픽 라이브러리와 아이콘 1,594개 전체가 들어 있었습니다. 문서 변환·그래픽은 필요할 때 불러오게 하고, 아이콘은 디자인 시스템이 관리하는 615개 세트로 바꿔 **첫 로딩 JS를 909kB에서 692kB로 24% 줄였습니다**. 이런 문제는 소스만 봐서는 보이지 않아서, 빌드 결과물을 검사해 같은 문제가 다시 들어오면 CI가 실패하도록 했습니다.

화면 테스트는 있었지만 파이프라인에서 돌지 않았고, 테스트가 흉내 내는 API 경로도 실제와 달라져 있었습니다. 백엔드만 가짜로 바꾸고 나머지는 실제 코드가 도는 테스트 환경을 만들어 MR마다 돌게 했고, 앱이 부르는 API 경로를 백엔드가 공개한 명세와 대조하는 검사도 넣었습니다. 이 검사로 **문서 탐색 경로가 늘 현재 위치만 보이던 버그**를 찾아 고쳤습니다.

백엔드 일부가 실패하면 화면 전체가 무너지기도 했습니다. 인증 서버가 응답하지 못하면 로그인 화면과 첫 화면을 끝없이 오갔고, 모델 목록 조회 하나가 실패해도 대화 화면 전체가 에러로 바뀌었으며, 오프라인에서 보낸 메시지는 입력창에서 지워진 채 사라졌습니다. 인증 실패를 만료와 확인 불가로 나눠 확인할 수 없을 때는 제자리에서 다시 시도하게 했고, 에러는 실패한 영역 안에서만 보이게 좁혔으며, 전송에 실패하면 입력을 남기게 했습니다. 위 테스트 환경에서 실패를 일부러 일으켜 하나씩 확인했습니다.

Surro Q&A 웹에서는 메뉴 API가 실패하면 빈 화면이 되던 운영 어드민의 메뉴와 정보 구조를 다시 설계했고, 답변의 근거 위치를 하이라이트하고 HWP·Word 미리보기와 문서 내 검색을 지원하는 문서 뷰어를 만들었습니다. 텍스트 API가 없는 HWP·Word는 화면에 그린 문서에서 글자를 뽑아 검색할 수 있게 했습니다.

### 지식베이스 Q&A — 문서 기반 AI 답변 서비스

**써로마인드** · 2025.11 ~ 2026.06 · 프론트엔드 개발, 문서 처리 백엔드 · 기여도 30%

**Tech** · Next.js 15, React 19, Zustand, TanStack Query, SSE, Vitest, Playwright · Python · Rust

문서를 올리면 그 문서를 근거로 AI가 답변하는 서비스입니다. 프론트엔드로 시작해 문서 처리 백엔드와 PDF 파서 연구까지 맡았습니다.

가장 먼저 해결한 건 **스트리밍 응답의 안정성**이었습니다. AI 답변은 SSE로 조금씩 나눠 들어옵니다. 요청과 파싱은 Web Worker로 옮기고, 마크다운 렌더러가 렌더할 때마다 커스텀 컴포넌트를 새로 만들어 답변 화면 전체를 다시 마운트하던 문제를 고쳤습니다. 연결을 여는 단계의 재시도와, 오프라인일 때 보낸 질문을 재연결 후 보내는 처리도 넣었습니다.

다음은 **답변을 믿을 수 있게 만드는 것**이었습니다. 처음에는 출처를 눌러도 PDF가 해당 페이지로 이동할 뿐, 어느 문장이 근거인지 보여 주지 못했습니다. PDF는 캔버스에 그려지기 때문에 DOCX·TXT에서 쓰던 하이라이트를 그대로 쓸 수 없었고, 페이지가 아직 로드되지 않았거나 머리글·공백이 달라 문장이 맞지 않으면 하이라이트가 실패했습니다. PDF의 텍스트 레이어에서 근거 문장을 찾도록 하되, 대상 페이지를 먼저 불러오고 렌더가 끝난 뒤 다시 시도해 타이밍을 맞췄고, 공백을 정규화해 여러 구간으로 후보를 만들어 매칭했습니다. 이제 PDF·DOCX·TXT 모두 출처를 누르면 근거 문장으로 이동해 표시되고, 한 문서에 인용이 여러 개면 차례로 넘겨 볼 수 있습니다.

문서 뷰어는 PDF·DOCX·CSV·TXT가 파일을 각자 불러오고 오류도 각자 처리하고 있어서, 같은 오류가 두 곳에서 처리되고 CSV 한글 깨짐 같은 수정도 뷰어마다 따로 해야 했습니다. 저장소 링크를 바로 열면 다운로드 헤더 때문에 PDF가 그려지지 않고, 서버에서 변환된 파일은 확장자가 달라 엉뚱한 뷰어가 열리는 문제도 있었습니다. 파일을 받아서 열고 형식은 실제 파일 기준으로 판단하게 한 뒤, 포맷별 읽기 방식만 따로 두고 **불러오기·취소·오류 처리를 훅 하나로 모았습니다**. 이후 뷰어를 다시 열 때 생긴 오류는 이 훅 한 곳만 고쳐 네 포맷에 함께 반영했습니다. 큰 PDF는 화면 근처 페이지만 그리도록 지연 로딩과 가상 스크롤로 처리했습니다.

이후 **문서 처리 백엔드**까지 맡았습니다. 문서 처리 방식을 조사해 보고서를 쓰고, 업로드부터 분류, 파싱, 청킹, 임베딩, 검색 색인까지 이어지는 백엔드를 구축했습니다. 이어서 Rust로 PDF 파서를 만들어 문서 56개(5,823쪽)를 초당 약 280쪽으로 처리하고 본문의 99.96% 이상을 보존했습니다(자체 측정). Surro Q&A에 도입할 계획이었으나, 다른 과제에서 만든 파서를 쓰기로 하면서 적용되지는 않았습니다.
